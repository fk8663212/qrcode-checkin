# 後續多活動規劃

狀態：**已記錄、延後；待目前活動結束後再評估實作**。本文件是後續設計依據，列出的功能尚未提供。

## 現行範圍

每次部署服務單一活動，提供事前設定；名冊、票券、帳號與報到紀錄保留。活動名稱變更只影響同一場活動的顯示，不會建立另一場活動。沿用目前每場最多 200 人的設計。

## 後續方向

1. **活動場次分開管理**：活動清單呈現名稱、類型、時間、狀態與報到數；例如 2026 與 2027 導生晚宴是不同場次。
2. **各場資料獨立**：每場分別管理名冊、票券、報到、匯入預覽、統計、稽核及工作人員權限。參加者編號改為同一場內唯一，異場可重複使用；同一人參加不同場次，票券與報到狀態獨立。
3. **避免跨場核銷**：工作人員先選定活動，頁首持續顯示目前場次；伺服器及資料庫共同驗證場次和操作權限。只在畫面篩選資料不足以隔離活動。
4. **活動類型與主題**：共用電子報到核心，以設定決定桌次、座位或組別等欄位是否顯示；黑金晚宴保留為可選主題。類型設定不代表另一個活動場次。
5. **複製活動**：可複製外觀及欄位設定，明確選擇是否帶入名冊。新場次產生新票券及未報到狀態，原場次的票券與歷史保留。
6. **主辦單位**：商業化時評估每個客戶各自擁有活動清單及人員權限；多客戶隔離與收費方式另行設計。
7. **互動功能**：單一活動的賓果已依後續要求完成整合，見 [賓果文件](BINGO.md)。多活動版仍需讓各活動的遊戲局次、資格、得獎及抽獎紀錄分開管理。

## 實作前需決定

- 活動開放報到時間、結束及封存規則；排定活動時間與開放報到時間分開考慮。
- 首期是同一主辦單位的多活動，或同時提供多客戶；資料庫、帳號及維運安排需配合。
- 哪些欄位確實需要可自訂，哪些保留固定規則，避免過早建立複雜的範本引擎。
- 現有活動如何遷移成第一場活動，以及既有票券連結如何維持有效；先完整備份並在副本驗證。

## 必要驗收

- A 活動票券不能在 B 活動核銷；未授權工作人員不能讀取、搜尋或匯出其他活動資料。
- 同名或同編號資料在不同活動互不覆寫，CSV 重匯只更新指定活動。
- 報表、有效報到唯一性、撤回、補發及安全重試皆限於正確場次。
- 複製活動不複製舊 token、報到狀態或歷史；原活動紀錄保持完整。
- 現有票券及歷史在遷移後保留；多場同時運行需另做容量與並行驗證。

這些項目不會因新增事前設定而自動啟用。現行決定見 [ADR-0001](adr/0001-single-event-deployment.md)。
